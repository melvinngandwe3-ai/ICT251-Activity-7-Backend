## Project overview
This is an independent REST API for the IT Support Desk system selected in Activity 6. It records student requests for Network, Software, Hardware and Account support. It uses Node.js, Express and a persistent PostgreSQL database.

## Requirements
- Node.js LTS (18 or newer recommended)
- npm
- PostgreSQL database
- Postman or another API client

## Project files
- `server.js` — Express app, API guide, health check, startup database setup and error handling.
- `routes/records.js` — GET, POST, PUT and DELETE routes with server-side validation.
- `db.js` — PostgreSQL connection pool.
- `schema.sql` — creates the records table.
- `seed.sql` — inserts eight made-up records once.
- `.env.example` — example environment variables. Never commit your real `.env` file.

## Run locally
1. Create a PostgreSQL database (for example, `it_support`).
2. Copy `.env.example` to `.env` and enter your database connection string.
3. Run `npm install`.
4. Run `npm start`.
5. The server creates the records table and inserts the eight sample records if the table is empty.
6. Open `http://localhost:3000`.

## Data agreement
Each record has:
- `id`: positive whole number generated by the database; do not send it in POST or PUT.
- `title`: 3–80 characters.
- `category`: 2–40 characters.
- `description`: 5–300 characters.
- `status`: exactly `Pending`, `In progress`, or `Completed`.

The POST and PUT body must contain all four editable fields. Text is trimmed before validation. PUT replaces all four editable fields and does not create a missing record.

### Example POST or PUT JSON
```json
{
  "title": "Cannot connect to campus Wi-Fi",
  "category": "Network",
  "description": "My device connects but cannot access the internet.",
  "status": "Pending"
}
```

## API routes
| Method | Route | Purpose |
|---|---|---|
| GET | `/` | API guide for the marker |
| GET | `/health` | Check server and database |
| GET | `/api/records` | Read all records |
| GET | `/api/records/:id` | Read one record |
| POST | `/api/records` | Create a record |
| PUT | `/api/records/:id` | Replace all four editable fields |
| DELETE | `/api/records/:id` | Delete a record |

## Responses and validation
- GET all: 200 and an array (or an empty array).
- GET one: 200 and one record.
- POST: 201 and the saved record including its generated id.
- PUT: 200 and the updated record with its original id.
- DELETE: 200 and `{"message":"Record deleted."}`.
- 400: invalid input, invalid ID or malformed JSON.
- 404: record or route not found.
- 500: unexpected server failure.
- 503: database unavailable at the health check.

The API checks field types, trimmed lengths, allowed statuses and positive whole-number IDs. It uses SQL placeholders to keep user input separate from SQL statements.

## Test with Postman
1. GET `/health` and confirm HTTP 200.
2. GET `/api/records` and confirm a JSON array with at least eight sample records.
3. POST a valid example body and save the returned id.
4. GET `/api/records/{id}` and confirm the created record.
5. PUT the same id with all four editable fields and confirm the id remains unchanged.
6. DELETE the same id and confirm the deletion message.
7. GET the deleted id and confirm HTTP 404.
8. Try missing fields, invalid status, malformed JSON, invalid ID and a positive ID that does not exist.

A Postman collection is included as `postman_collection.json`. Change its `baseUrl` variable to the live URL after deployment.

## Deploy
The assignment asks for a live backend base URL. Deploy this repository as a Node.js Web Service on Render or a lecturer-approved equivalent:
- Build command: `npm install`
- Start command: `npm start`
- Add `DATABASE_URL` with the hosted PostgreSQL connection string.
- Set `DB_SSL=true` if the database provider requires SSL; otherwise use `false`.
- Set `CLIENT_ORIGINS=*` for the classroom API demo, or use the exact frontend URL later.
- Set `PUBLIC_BASE_URL` to the assigned HTTPS service URL.

The server runs `schema.sql` and `seed.sql` at startup. The database must be persistent; do not rely on temporary local files. After deployment, test the health route and all CRUD routes using the live URL. Free hosting may pause when idle, so the first request can take time.
